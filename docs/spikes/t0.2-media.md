## 2. 工程教训（对 M0+ 有直接约束）

动态插件迭代 v1→v8 共 8 版，踩坑全部来自真实运行时校验，沉淀如下：

1. **动态 Tool 注册契约**（M2 T3.3 直接复用）：
   `harness.defineTool({ name, description, parameters, output: { schema, render }, execute })`；
   - `output` 必填，`output.render` 必须是函数且返回**内容块数组** `[{type:'text', text:'...'}]`；
   - `output.schema` 走 dsh-tools value-schema DSL：object 必须**显式 `additionalProperties: true/false`**、不支持顶层 `required`/`items` 细化——用最小 `{type:'object', additionalProperties:true}` 即可；
   - 注册必须 `harness.registerTool(ctx, harness.defineTool({...}))`，裸对象会被拒。
2. **RPC 返回必须无损 JSON**：`harness.handle` 的 handler 返回值中出现 `undefined` 字段即抛错——构造返回对象后逐字段赋值，勿把可能为 undefined 的值放进去。
3. **`fs.writeText`（Host 半边动态插件内）静默失效**：v2 起反复验证 resolve+writeText 无异常但文件不落盘（工作区/DSH 目录均无）。**M0 起凡是插件要持久化，一律走动态 Tool / RPC 回主控或业务 Service，不依赖 fs 直写**；待查项：`FsWriteIntent`（`expected` 参数）是否必需。
4. **通信通道选型**：Client→Host 用 `host.call`；**Agent 读插件状态用动态 Tool**（本次 `meeting_spike_report` 即此模式，M2 的 4 个 meeting_* 工具同构）。
5. **`sandboxPolicy.workspaceRoot` 可用**（Host 侧 ctx.get），可作为插件定位工作区的规范方式。
